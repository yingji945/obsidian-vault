## 一、上线管理

### 1. ⭐「上线日」必须拆三层口径（配置上线 / 系统启用 / 商品面客）

- 📌 **实证**：7/16 定 8/1 → 7/17 提 8/4 → 7/20 拆「8/1 配置上线 + 8/5 面客」→ 7/29「原计划明日上线」→ 7/30 系统侧排期（原定晚 6~7 点，**压测拖到凌晨 4~5 点**）→ **8/4 00:00 系统启用（D-Day）** → **8/5 消费者首扫**。索引里「8月1日上线」的旧口径已废弃。
- ✅ **下次**：立项即定义三层 + 每层的「谁宣布 / 什么信号 / 对外怎么说」；**对外只用一个话术，对内分层排期**

### 2. ⭐ 风险清单按「不可逆 × 涉及外部账务」排序，不按物料/设计

- 📌 **实证**：7/26 盯防清单 7 条以物料/设计/客服为主；实际唯一 P0 是**财务打款（8/4 时已 7 天 0 进展）**，靠 B 降级预案「只发券、无需预充值」兜住（8/4 03:35 首巡触发条件）。
- ✅ **下次**：风险表加权重列（不可逆 / 涉外 / 可降级）；**每个涉外项必须配 B 方案 + 触发条件 + 谁有权拍板**

### 3. 值守节奏模板化：6h 一轮战报 + 矛盾识别法

- 📌 **实证**：8/4 四轮战报（03:35 / 09:35 / 15:35 / 21:35）+「**业务侧消停 vs 技术群冒新风险**」矛盾识别法已成型（[[一物一码/01-原始纪要/2026-08-04-D-Day知识沉淀|D-Day 知识沉淀]]）。
- ✅ **下次**：直接复用报送节奏与识别法，不重新设计值守

## 二、活动机制设计

### 4. ⭐「领奖动作」是转化漏斗，不是合规条款——上线前就要给出预期领取率

- 📌 **实证**：v7 规则下**所有奖品**（含 40% 概率的 15 元券）都需 48h 内「加企微 luna」**或**「复购第二瓶」；实测领取率 **8 月 37.6% → 9 月 38.6%**（规模涨 5.3 倍而比率几乎不动）→ 结构性摩擦，**6 成流量在此流失**。
- ✅ **下次**：设计期就为领奖动作定目标值 + 做 A/B（提示时效 / 动作前置 / 失败重试）；**当漏斗管，不当免责声明写**

### 5. 中奖率用「期望人数表」校准，别用直觉判故障

- 📌 **实证**：365 张券 0.0001% → 月期望 **0.18 人**、P(0)=84% → 两月 0 中出**完全正常**（我一度误判为档位失效，经 v7 规则 + 6 档全量反算纠正，实测/期望比 0.98~1.66）。
- ✅ **下次**：拿到规则**先算期望人数表**再判异常；同时评估「宣传语 vs 概率」的数量级落差（期待管理 / 合规）

## 三、数据与归因

### 6. ⭐ 先证伪「运营驱动」，再谈活动效果

- 📌 **实证**：按天曲线与**铺货节点**一一对应（8/9 出库 117 → 8/10 生椰 128 → **8/20→8/21 三口味 1,198→1,540**）；**周末效应≈0**（8 月周末 1,127 vs 工作日 1,036）→ 增长=供给驱动，运营可撬的只有领取率。
- ✅ **下次**：复盘第一步做「供给 vs 需求」归因；**KPI 分母落在供给侧**（铺货量 / 扫码量），避免把铺货涨量记成活动功劳

### 7. 每个「率」都写清分子分母，跨表先做口径表

- 📌 **实证**：发放率反推分母 31,291 vs 选择人数 34,236（差 8.6%）；趋势表参与 33,016 vs 奖品表 34,236（3.7%）；红包「选择 12,852 vs 到账 3,653」。三处对不上 → 结论会被质疑。
- ✅ **下次**：出数前先出一页**口径表**（分子 / 分母 / 去重粒度 / 时间窗 / 数据源），跨表差异逐条给解释

### 8. 成本看「结算单价」，不看面值

- 📌 **实证**：15 元即享券按 **15 元 / 3.3 元 / 0 元**记账，9 月费用差 **40 倍**（140.4 万 vs 33.6 万 vs 3.5 万）→ ROI 根本判不了。
- ✅ **下次**：预算评审即锁定**记账单价 + 结算周期**（N+3 等），复盘全程只用这一个口径

## 四、跨团队推进

### 9. 卡点推进＝单笔样本验证 + 明确归属 + 写死期限

- 📌 **实证**：7/22 财务衔接 → 7/23 用一笔 0.4 元红包（transfer_number 与业务凭证号**尾号 2672 匹配**）验证字段对齐 → 7/24 定位「记账时间在支付系统、不在我方」→ 权责切割、财务后续直连支付侧 → 8/3 因「一元红包」对接叫停 → 8/12、8/14 结算闭环。
- ✅ **下次**：**用一笔真实样本走通全链路**，比开会催有效；同时把「谁负责」写进纪要并定期限

## 五、组织与治理（用户补充 · 2026-10-07 原话）

### 10. ⭐ 一开始就该按「项目制」立治理结构：一个核心负责人 + 各职能子负责人

- 📌 **实证（用户原话）**："如果是在一开始我们有意识的把它当作是一个项目去做推送，有一个核心的项目负责人，然后下面有几个子项目负责人，这样去推动，可能会好一些，比如可以从：**品牌负责人、财务负责人、运营负责人、商业分析负责人**等，这样的视角上去出发，或者去统筹项目会好很多。"
- 🔻 **现实处境（同一原话）**："这里面其实尴尬的地方，是**我在推动财务、技术、以及运营、以及商业分析**"——运营单点横向推 4 个职能，无授权、无资源抓手，全靠个人推动力。
- ✅ **下次**：立项即设「核心项目负责人 + 4 条线子负责人（品牌/财务/运营/商业分析）」，每条线对**同一批上线里程碑**负责、进同一张责任表；核心负责人只做**集成 + 决策 + 对外**，不做逐条推销（对应 [[一物一码/02-业务视角/02-角色责任矩阵\|角色责任矩阵]] 的演进版）。

### 11. ⭐ 关键干系人（财务 VP）必须在方案定稿前进入，否则后期返工改接口

- 📌 **实证（用户原话）**："在一开始的时候，如果**财务 VP 方能够在尽快进入项目中做对齐，那么系统上不会做切换、做改造，变成要重新更换企业系统的接口**等。"——即：晚进入 = 方案返工 + 换企业系统接口（真金白银的工程代价）。
- ✅ **下次**：立项会必到名单＝**品牌 / 财务 / 法务 / 技术 / 数据的一把手（VP 级）**；对任何「会改系统架构/结算链路」的诉求设**准入检查点**——**财务未对齐，不进入开发**（本项目财务线一直拖到 7/22 才衔接、8/3 因「一元红包」被叫停，是同一根因的延续）。
