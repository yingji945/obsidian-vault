## 二、核心字段映射表

| 业务概念 | 源系统（业务库） | 数仓字段 | 看板/取数位置 | 备注 |
|:--|:--|:--|:--|:--|
| 活动标识 | `t_rtd_cap_activity.activity_no` | `dim_inst_rtd_cap_activity_d_his.activity_no` | 全局筛选维度 | `marketing_scene='CAP_INNER'` 即瓶内营销 |
| 活动状态 | `enable_status` / `activity_status` | `enable_status`(1/2/3) · `activity_status`(1/2/3) | 活动筛选 | **两者都要判**：可「已启用未开始」 |
| 参与人 | `participate_log.member_id` | `ads_inst_cap_activity_win_grant_d_inc.mem_id` | 参与人数/参与率 | ⚠️ 字段改名 `member_id`→`mem_id` |
| 扫码身份 | `participate_log.scan_id` | `ads...scan_id` | 首扫/复扫（跨表关联键） | 与 `record_user_line.first_scan_id` 构成双唯一键 |
| 参与阶段 | `participate_phase`(1首扫/2复扫) | `participate_phase` | 首扫量 / 复扫量 | — |
| 拦截层 | `layer_break_code` | `layer_break_code` | **7 级漏斗各层通过率** | 空=未拦截 |
| 中奖结果 | `hit_result`(0未中/1中) | `hit_result` | 参与 vs 中奖 | ⚠️ 活动级「中奖」口径在 PRD 里写作 `hit_result=3`，实测业务库为 0/1，**上线后需与开发二次确认**（现存口径冲突） |
| 中奖记录 | `record_user_line.id / activity_record_no` | `record_id` / `activity_record_no` | 中奖人数/中奖率 | 中奖 ≠ 履约成功 |
| 奖品命中 | `record_user_line.prize_row_id` → `activity_prize.id` | `prize_row_id` · `prize_name` | 各档奖品发放 | 奖品配置快照 |
| 内容类型 | `activity_prize.content_type`(RED_PACK/INSTANT_COUPON/COFFEE_COUPON/COFFEE_STORE_COUPON) | `base_content_type` | 券类型分布 | 与 `prize_content_value`（方案编号）联合校验 |
| 获得方式 | `activity_prize.prize_grant_mode` / `expand_option.prize_expand_mode` | `base_grant_mode` · `expand_grant_mode` · `final_grant_mode` | 加C / 复购 / 直接三条路径 | 基础与膨胀**独立配置** |
| 膨胀选择 | `record_user_line.record_prize_status`(2领取/3膨胀) | `is_expand` · `is_expand_support` | 膨胀率 / 直接选择率 | 行级权威：`activity_prize.is_expand=1` |
| 膨胀选项 | `record_user_line.expand_option_id` → `activity_prize_expand_option.id` | `expand_option_id` · `expand_prize_name` · `expand_target_type` | 膨胀奖品分布 | **二期 1:N**（一奖品多膨胀选项） |
| 履约状态 | `record_user_line.fulfillment_phase` | `fulfillment_phase` | 发放率 / 履约漏斗 | 取值见业务流程图第三节 |
| 履约失败 | `fulfillment_fail_code` / `_reason` / `_time` / `fulfillment_retry_count` | `fulfillment_fail_code` / `_reason` / `_time` / `fulfillment_retry_cnt` | 异常监控 | 主动延后（未加C/未复购）**不写**失败码 |
| 红包实例 | `t_rtd_redpack_user_instance.instance_status`(20/30/40/50) | `redpack_instance_cnt` · `redpack_transferred_cnt` · `redpack_transferred_amt` | 红包到账率 / 费用 | **50=已打款成功** |
| 红包费用 | `t_rtd_redpack_user_instance.redpack_denomination` + `transfer_done_time` | `redpack_transferred_amt` | 现金红包费用 | 以到账为准 |
| 售卖量 | `ads_inst_shop_sku_order_summary_10min_d_inc_uniq`（`SUM(spec_num)`） | — | 全渠道/线上/线下售卖量 | 与 `activity_no` **不关联**（售卖独立归因） |
| 曝光 | 埋点 `lottery_main_page_bw` · `open_id` · `properties.activity_no` | —（不在 ADS 宽表内） | 曝光人数/参与率分母 | openid 去重，⚠️ 不是 mem_id |
| 加C | `lucky_wecom.t_wecom_external_user(_history)`（`member_id` / `wx_unionid` / `state` / `added_user_time`） | —（待建/待确认） | 加C人数/加C率 | `state` 需填真实渠道名（待提供） |
| 会员注册 | `lucky_member.t_member.created_time` | — | 新增注册人数 | created_time = 注册时间 |
| 券发放 | `lucky_marketing.t_mkt_coupon_send_record` + `t_mkt_coupon`；咖啡库券 `lucky_coupon_order.t_mkt_coffee_coupon_send_record` | 部分进 ADS 的 `*_grant_cnt` | 券费用 / 券核销 | 即享券/咖啡券/库券分别取 |
| 订单复购 | 自营订单表（`merchant_type=0`，有效状态 `2/3/7/8/9/10`） | — | 成交/复购人数 | 见 [[dws_eorder_eorder_d_his_combine]] |

> ⚠️ **口径边界（PRD V1.1 明确）**：ADS 宽表覆盖 参与→中奖→膨胀→履约；**曝光 / 加C / 复购 / 售卖量 / 券核销不在宽表内**，需另接埋点与明细模型——这正是「人数跨奖品、跨路径必须重新去重」「活动总量不得由奖品路径行求和」两条原则的由来。

## 三、23 项 P0 指标 → 取数入口（源自活动效果取数文档）

| 指标 | 取数方式（表 + 字段/口径） |
|:--|:--|

| 参与人数 / 参与次数 / 人均参与次数 | `t_rtd_cap_participate_log`：`count(distinct member_id)` / `count(*)`（`create_time` 窗口） |
| 中奖人数 / 中奖次数 / 中奖率 | `t_rtd_cap_activity_record_user_line`：`count(distinct member_id)` |

| 新增注册人数 | `lucky_member.t_member.created_time` |
| 加C人数 | `lucky_wecom.t_wecom_external_user_history` ⋈ `t_wecom_external_user`（`state`=活动名、`added_user_time` 窗口），`count(distinct member_id / wx_unionid)` |
| 成交人数 / 复购人数 | 自营订单表（口径待定） |
| 膨胀人数 | `record_user_line.record_prize_status=3` 且 `activity_prize.is_expand=1` |

| 奖品总费用 | 红包 + 现制饮品券 + 即享券 三项之和 |

## 四、上线段口径补充（7/16~8/5 纪要 + 8/4 D-Day 沉淀回填）🆕

> 来源：[[2026-07-16|统计对齐会（原件全量口径）]] · [[2026-07-23]] · [[2026-07-24]] · [[2026-07-31]] · [[2026-08-03]] · [[2026-08-04-D-Day知识沉淀]] · [[2026-08-05]]

| 主题 | 口径 | 出处 | 对取数/看板的影响 |
|:--|:--|:--|:--|
| 中奖记录状态 | **仅保留 1/2/3，状态 4（作废）直接排除**，不进任何统计 | 7/16 原件 | 所有中奖/履约口径都要加 `record_prize_status <> 4` |
| 待选状态 | 中奖后**未做选择的「待选」纳入参与人数**，不做排除 | 7/16 原件 | 参与人数口径 |
| 未登录 | **未完成登录授权不计参与人数**，仅落扫码流水表 | 7/16 原件 | 参与人数/漏斗分母 |
| 非中奖分母 | 风控拦截、未登录导致的非中奖扫码**从扫码流水表取**，补充活动级分母 | 7/16 原件 | 7 级漏斗分母 |
| 活动标识 | 埋点 `activity number` = **后台活动ID**（非单奖品行ID）；曝光只从埋点层取 | 7/16 原件 | 曝光取数入口 |
| 获取方式 | 取 `price_grant_mode`，**以用户最终选择实际奖品为准** | 7/16 原件 | 加C/复购/直接三条路径 |
| 行为归属 | 按用户**最终选择**的行为记录；**不统计初始 vs 膨胀归属**，避免重复计数 | 7/16 原件 | 膨胀率/直接选择率 |
| 100% 中奖 | 参与人数 **= 中奖人数**（暂为等值）；非 100% 活动再拆 | 7/16 原件 | 中奖率口径 |
| 「首次」类指标 | **暂不纳入**正式统计（口径模糊），验证后再入体系 | 7/16 原件 | 首次膨胀/首次直接选择人数 ⏸️ |
| 发放完成判定 | 以**用户完成获取动作（加C/复购/直接领取）**为准，**非后台配置的发放动作** | 7/16 原件 | 发放率口径 |
| 费用取值 | 优先**微信商户号实际到账**，后台发放状态交叉校验；误差以第三方对账为准，**不做人工修正** | 7/16 原件 | 现金红包费用 |
| 记账触发 | **仅扫码中奖未完成第二笔复购 → 不发券、不纳入账务统计**；活动后未领奖资格作废 | 8/5 晚 | 红包费用/收入确认时点 |
| 记账时间字段 | **存储在支付系统**（非我方业务库）；对接物 = 我方**红包流水号** + 支付侧**全量红包关联信息** | 7/24 | 财务对账链路 |
| 凭证匹配 | 自有系统 `transfer_number` ↔ 商户账单**业务凭证号**（尾号一致，已抽样校验） | 7/23 | 红包费用对账 |
| 券有效期 | 中奖券增设 **24 或 48 小时**有效期（引导及时复购）；宣讲口径为 **48h 内兑奖、逾期失效** | 8/5 ×2 | 券口径/失效统计 |
| 拼团上报 | **成团后上报支付数据；未成团自动退款时同步上报退款数据**（毛总确认） | 8/3 | 订单/复购口径（含退款扣减） |
| 数据同步时效 | 活动数据同步**无固定周期**（**非实时、非 T+1**），延迟由**微信侧接口节奏**决定 | 7/31 | 看板时效预期（勿按 T+1 假设） |
| 预测成本单价 | **9.9 元券 = 0 成本 / 0.5 折券 = 3.3 元 / 通用优惠券 = 15 元**（刘晋泽新增预测成本列） | 8/3 | 费用预估与总投入核算 |
| 奖品量级 | **6 档常规奖品 / 后台实际配置 23 项奖品**；中奖率可动态调整 | 8/5 | 各档奖品发放口径 |
| 即享券规模 | 即享券**累计发放总金额仅十余万元** → 不做系统改造，走电商券管理模块自查 | 7/31 | 费用量级锚点 |
| 查询承压 | 客服专用券查询工具**单次跨度过大会导致业务库崩溃、影响正常发券** → 另建大数据出口 | 8/3 | 取数方式约束（勿直查业务库） |
| 财务系统接入 | **活动数据当时均未接入财务系统**；因「一元红包」疑问**对接已叫停** | 8/3 | 财务对账状态（8/12、8/14 才闭环） |
| 中奖率双口径 | 「**综合中奖率 100%**」（活动层）与「**咖啡券中奖概率 1%**」（奖品层）**不冲突**：人人有奖、咖啡券稀缺 | 8/3 + 8/5 | `hit_result` 口径澄清（见待补第 2 条） |
| 曝光下钻 | 曝光**不支持下钻单奖品**（前端未上报单奖品点击） | 7/16 原件 | 单奖品曝光不可取 |
