# 02-我的认知更新（刘晋泽）

> 以下为用户**原话整理**（保留原表述，仅编号与补充实证）；每条 = 原话 → 项目实证 → 形成的判断。

---

## 一、更谦逊：先听别人在说什么，先了解别人的视角

> 📌 **原话**："谨慎，先听别人在说什么，了解别人的视角。比如，我从没想过**财务入场的问题会影响到这么多**，有很多的系统是我不了解的、不清楚的，我应该**更加谦逊**。"

- 🔗 **项目实证**：财务线直到 **7/22** 才正式衔接 → **7/24** 才发现「记账时间字段在支付系统、不在我方」→ **8/3** 因「一元红包」对接被叫停；同理还有税负临界点、券配置金额=门店入账金额等——都不是运营本职知识。
- 🧭 **形成的判断**：跨职能项目里最大的风险不是"做错"，而是「**我不知道我不知道什么**」。不熟的领域要当**风险源**管理（谁负责、门禁问题是什么），不能当执行细节。
- ➕ 关联：[[一物一码/06-复盘升华/01-方法论沉淀\|方法论沉淀]] #11（阶段门禁）、#15（税负）、#34（券配置金额）

## 二、流程先定、且要"让人有感知"；疑问当场提，别等开发中再改

> 📌 **原话**："先定下**用户体验的流程**是什么样的，让**老板是有感知的**；在一开始，有建议和疑问就提出来。关于**加 C 的链路、以及复购的链路，其实变更过好多次**，研发是有一些压力的，项目已经在开发中了，因为**核心的诉求一直想要更改，研发一直要倒推项目**。"

- 🔗 **项目实证**：6/17 链路从 **14 条链路 14 个码**收敛为 1 个 luna 码 + 欢迎语 + 中奖页；6/25 又提「加 C 跳转与复购领取的用户认知混淆」；7/13 孙晓伟「复购二瓶的奖励没有膨胀了吗？我咋记得是有的」。
- 🧭 **形成的判断**：**需求变更的代价最终落在研发排期上**（"研发一直要倒推项目"）。核心诉求必须**先冻结再开发**；变更要让相关方**有感知**（老板/研发/财务都知道），否则是隐性返工。
- ➕ 关联：#12（北极星先签字）、#23（配置冻结→校准规则→提审）、#33（变更回同步决策人）

## 三、不要按自己的理解下结论——勤问、多了解，哪怕让人烦

> 📌 **原话**："不要总是按照自己的理解去想事情，有很多地方是你未知的地方，要先去了解，**不要下结论，勤问，多了解，哪怕很让人烦**。"

- 🔗 **项目实证**：7/16 统计口径 **12 条**全靠追问才对齐；8/3 因「一元红包」理解不一致导致财务对接叫停；我自己也曾把「365 张券 0 中出」误判为故障（实为 0.0001% 概率的正常结果）。
- 🧭 **形成的判断**：这个项目里最有效的工作方式是「**先问再说**」——口径、字段、约束都握在别人手里；用**一笔真实样本**（如 0.4 元红包凭证尾号 2672 匹配）验证，比读十份文档可靠。
- ➕ 关联：#9（单笔样本验证）、#7（口径表）、#5（期望人数表）

---

## 📌 三条的共同线索

> **把"我以为"换成"我去问"**：谦逊 → 先了解别人的视角；流程 → 先冻结再开发、变更要有感知；方法 → 不下结论、勤问多验证。
> 这三条不是流程问题，是**工作姿态**问题——也是这个项目给用户最大的认知更新。
