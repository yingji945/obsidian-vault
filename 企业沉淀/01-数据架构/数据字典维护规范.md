# 数据字典维护规范

> 本文档面向数据字典的维护者（Hermes 或后续接手的人），说明新增、修改、删除表文档的流程。

---

## 新增一张表

### 触发条件

- 用户发送 `SHOW CREATE TABLE` 或 `SELECT` 完整字段列表
- 发现数仓中新增了之前未记录的表

### 执行步骤

```
用户发 DDL
    ↓
第1步：建表文档 → 企业沉淀/数据字典/{业务域}/{表名}.md
第2步：更新索引 → 企业沉淀/数据字典/数据字典索引.md
第3步：关联相关表 → 对应的表文档加上双向链接
第4步：git commit + push
```

**目录结构（2026-10-13 起 · 按业务域分目录）**

```
企业沉淀/数据字典/
├── 数据字典索引.md            ← 入口（按业务域分类）
├── 门店业务域/   一物一码域/   埋点日志域/   电商域/
└── 企业微信域/   公域域/       瓶内营销域/   CDP用户运营域/
```

**新表一律按域建在对应子目录**，不再堆在根目录；判域规则见下方「域划分约定」。
（此前平铺 25 张已按域归位；改名历史：订单交易域 → 门店业务域）

#### 第1步：建表文档

> ⚠️ **动手前先核对分簇阈值**：先看当前表数与分簇阈值（口径见《知识库整理规范》第七章，实现在 `/opt/data/scripts/check_vault_clusters.py`）。**已超标就本次一并分簇，不许写「以后再评估」** —— 这类无触发点的条款曾让 25 张表超标运行 2 个多月（详见 [[我的体系观]] 第九章）。
> 当前状态：25 张 / 已分 8 个域目录（2026-10-13）。

每张表独立一篇，包含以下章节：

| 章节 | 内容 | 必须 |
|:----|:-----|:----|
| YAML frontmatter | `created`, `updated`, `tags`, `field_status`, `source` | ✅ |
| 表名 + 数据库 | 完整表名、所属数据库 | ✅ |
| 表结构 | 字段名、类型、说明（带编号表格） | ✅ |
| 关联键 | 关联了哪些表、用什么字段 join | ✅ |
| 使用注意点 | 分区、口径、陷阱、常见误解 | ✅ |
| 典型 SQL | 1~3 条常用查询示例 | 推荐 |
| 关联 | 双向链接到相关表、索引页 | ✅ |

**字段分组规则**：字段多时按逻辑分组（基础标识/时间戳/金额/状态等），每组一个小表格。

**字段清单格式**：

```markdown
| # | 字段名 | 类型 | 说明 |
|:-:|:------|:----|:-----|
| 1 | `id` | bigint | 自增主键 |
```

#### 第2步：更新索引

在 `数据字典索引.md` 中：

1. 找到对应的**业务域**（企微/公域/电商/一物一码/埋点日志）
2. 新增一行：`| `表名` | 说明（含字段数） | ✅ 完整 |`
3. 如果表属于新的业务域，在合适位置新增一个域名 + 表格

**索引表格格式**：

```markdown
## XXX域

| 表名 | 说明 | 字段数 | 层级 |
|:----|:-----|:-----|:----|
| `表名` | 简短说明 | N | `ODS/DWD/DWS` |
```

#### 第3步：关联相关表

- 在相关表的文档末尾「关联」行加上新建表名的双向链接
- 如果是 ODS→DWD 的数据血缘关系，标注 `（数据源ODS）`

#### 第4步：提交

```bash
cd /opt/data/obsidian-vault
git add -A
git commit -m "数据字典：新增 {表名} {N}字段"
git push origin main
```

## 修改一张表

### 触发条件

- 字段变更（新增/删除/改名/改类型）
- 使用注意点需要补充（踩了新的坑）

### 执行步骤

```
第1步：更新表文档
第2步：如果字段数变化，更新索引中的说明
第3步：git commit + push
```

### 版本记录

在文档的 YAML frontmatter 中更新 `updated` 字段，并在注意点中标注变更：

```
> ⚠️ 2026-07-25 更新：新增了 {字段名} 字段，用于 {说明}
```

## 删除一张表

不建议实际删除文档，改为在索引中标记为「已废弃」：

| ``表名`` | 原说明 | N | 层级 | ❌ 已废弃 |

保留历史记录供回溯。

## 原始 DDL 归档（2026-10-13 确立）

用户发来的 `SHOW CREATE TABLE` / 字段列表**原文，收到即归档**到 `企业沉淀/01-数据架构/原始DDL/`：

- 完整建表语句 → `{库}.{表名}.sql`
- 只有字段列表（`SELECT col, -- 注释` 形式）→ `{库}.{表名}.字段列表.sql`

**为什么要归档**：① 用户贴的原文**只存在于对话里、对话历史不落库**，解析完就丢 = 永久丢失（曾把原文留在临时目录，24 小时即被清理，靠及时发现才救回）；② 字典文档里的字段表是**程序化解析产物**，出现分歧时必须能以原文为准；③ 表结构变更时可 diff。

归档清单与「已知未归档」追踪见 [[原始DDL/README|原始 DDL 归档]]。

## 字段类型的两段式核定（2026-10-13 确立）

用户常先给**字段列表**（`col, -- 注释`）、后给 `SHOW CREATE TABLE`。类型按两段走，**第二段不许跳过**：

| 阶段 | 做法 | 文档标记 |
|:--|:--|:--|
| ① 只有字段列表 | 找**同族表**（同前缀 / 同数据源，如 `fact_dwd_log_c_*` 家族的另几张）交叉继承：先验两张同族表之间该字段**同名同类型零冲突**，再取值为**暂定** | 类型后标 `†` + 写「继承自同族表 X/Y，**待 DDL 核对**」；`field_status: 🟡 x/y 含类型` |
| ② DDL 到位 | **逐字段 diff**（暂定值 vs 真实值），全部按 DDL 落定 | 去掉 `†`；`field_status: ✅ 完整`；**新增「类型核定记录」节留痕**（写明错了几个、错在哪类字段） |

**为什么要留痕**：实测某表 39 个继承值里 **8 个是错的（≈21%）**——全是「承载型」字段：`id` 类（同族 `varchar` / 本表 `bigint`）、经纬度（`decimal` / `string`）、时间（`datetime` / `string`）、平台（`tinyint` / `int`）。
**同族表同类型只证明「那两张彼此一致」，不证明「与本表一致」**——不同 fact 表的清洗/写入方式不同。把暂定值当结论去写 `cast`/聚合会直接错。

**反向陷阱**：埋点表大量语义为数值的字段实际以 `string` 承载（价格 `prop_cmdty_price`、经纬度 `longitude/latitude`、部分 id）——文档必须显式写「聚合/距离计算前先 `cast`」。

## 域划分约定（2026-10-12 确立）

**门店业务与电商业务分属不同域，不得混放**：

| 域 | 业务 | 表名前缀 | 典型表 |
|:--|:--|:--|:--|
| 电商域 | 即享商城（线上商城） | `eorder_*` | `dws_eorder_eorder_d_his_combine` |
| 门店业务域 | **门店零售订单**（线下取餐 + 门店配送）**+ 门店商品行为埋点** | `order_*`、门店侧 `fact_dwd_log_c_*` | `dwm_mg_order_cmdty_market_wide_d_view` |

两条业务线的口径、状态枚举、金额字段**均不通用**（例：门店 `order_status = 50`，电商 `2/3/7/8/9/10`）。
新表**按表名前缀判域**；拿不准先问用户，不擅自并入既有域。

## 通用原则

1. **完整优先于完美**——字段太多可以先建框架，标 `🟡 待补充`，等用户发 DDL 再补全
2. **每张表独立一篇**——不合并，方便搜索和链接
3. **关联不能断**——新增表必须检查是否有相关表需要加链接
4. **commit 信息清晰**——`数据字典：新增/修改 {表名} {N}字段` 的格式
