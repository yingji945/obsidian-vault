# 我的判断标准

> 这是我判断一件事「好不好」的原则。不是知识，是品味。
> 会随着经验持续更新。

---

## 一、什么样的 SQL / 数据分析算「好」

### 流程标准

一条好的 SQL 查询，在我的标准里：

```
   先给结论（一行+颜色信号）
   ↓
   数据带对比（不孤立的数字）
   ↓
   写明风险点
   ↓
   给出下一步
   ↓
   代码本身干净、能跑、能复用
```

### 代码标准

| 维度 | 好的 | 不好的 |
|:----|:----|:------|
| 性能 | 拆 OR 为 UNION ALL，不加无谓的 JSON 解析，小表广播 | 大表全扫、OR 里混 JSON、不用 broadcast hint |
| 可读 | CTE 分段清晰，别名有含义 | 一坨 WHERE + 20个 OR |
| 可复用 | 日期边界用变量风格，方便改范围 | 硬编码 `date_sub(current_date(),1)` 藏在里面 |
| 安全 | `NULL NOT IN` 加 `is null or` 保护 | 忘记 NULL 语义，净流量全丢了 |

### 关键原则

1. **不加无谓的复杂度**。能用一个 JOIN 解决别用两个，能用 IN 别用 OR。
2. **「好分析」= 能推动决策的分析，不是数据最全的分析**。
3. **结论先行，永远带对比，永远有下一步。** 这三个缺一个就是不合格。

## 二、什么样的 AI 协作模式算「好」

### 核心原则

> **AI 做大脑做编排，成熟工具做手脚。不要什么活都自己揽。**

这句话翻译成我的标准：

| 好的设计                         | 不好的设计              |
| :--------------------------- | :----------------- |
| Hermes 调三省六部做决策，调 API 发卡片    | 我自己写死所有逻辑          |
| 用飞书原生 Bot 拉文档，Hermes 整理入库    | Hermes 自己去解析飞书文档格式 |
| 三省六部讨论出结论，Kanban 记录，Web 旁路展示 | 三省六部自己记录+展示+通知     |
| 专业工具干专业活（Working Copy 同步手机）  | 我写个脚本自己做同步         |

### 更本质的一句话

> **你在设计的是「人机协作的组织架构」，不是在使用工具。**

三省六部、大脑+手脚、Hermes+Jacob 分工——本质上都是在搭建一个**组织**，再把自己放进最合适的位置。

## 三、什么样的「体系」算「好」

| 维度 | 好的体系 | 不好的体系 |
|:----|:--------|:----------|
| 清晰 | 每个角色/层级/位置职责明确 | 一个人什么都要做 |
| 边界 | 知道自己不能做什么 | 觉得自己什么都能做 |
| 可进化 | 有反馈机制，能迭代 | 建完就固定了 |
| 容错 | 有人犯错也不会全崩 | 一个人掉链子整个系统停 |

### 从三省六部学到的

三省六部最让我满意的不是它可以讨论问题——是它设计了一个**角色分界**。数据大臣只管数据和 SQL，运营大臣只管业务判断，法务大臣只管合规。

**每个人只做自己最擅长的事，比一个人强行全能有效得多。**
这个原则也适用于我自己——不是所有事都要自己干。

## 四、什么样的「公平」判断算「好」——看结构，不看动机

> 2026-08-23 从 [[关于我（持续构建）]] 确认加入。**「公平」不是立场问题，是结构问题：判断一个人/公司站在公平的哪一边，不看动机（赚钱/立人设），看结构（有没有堵住别人的取水口）。**

| 维度 | 站在公平一边 | 站在对立面 |
|:----|:--------|:----------|
| 取水 | 取水 + 偶尔倒水（哪怕是倒给利益） | 取水后堵住别人的取水口 |
| 动机 | 动机不重要——公地不审判动机 | 用「动机纯洁」当遮羞布 |
| 结构 | 只收税不种地（裁判不当运动员） | 既当裁判又当运动员 |

关键原则：

1. **赚钱 ≠ 不公**：真正不公的是「取水后堵住取水口」——闭源垄断、封路、open-washing。
2. **被利用的进步依然是进步**：制度被强者利用，不否定制度本身的进步性（科举被皇权利用，但知识向寒门开放是真实的）。
3. **当体系奖励封闭，连受害者都会选择封闭**——判断结构时，记得真正的控诉对象常常是体系，不是个体。

## 五、什么样的「积累」算「好」——什么值得存

> 2026-08-31 从 [[人生观/关于我（持续构建）|关于我（持续构建）]] 第二次更新确认加入。判断「什么值得积累」的真实标准。

### 一个关键判断

> **如果还在这个公司，会议纪要重要；如果不在了，就完全不一样。**

| 在公司的 | 离开公司的 |
|:--------|:----------|
| 一物一码 8月5日上线 | 你是怎么判断一件事好不好的 |
| 挂耳兑换 1200→800 分 | 你搭三省六部的思考方式 |
| 麻孜凯说了什么、黄翠说了什么 | 你写 SQL 的品味和标准 |
| 即享标签体系扩容规则 | 你在约束条件下找到增量路径的能力 |

**真正该积累的不是「这家公司的东西」，而是「在这家公司经历中，你自己长出了什么」。**

### 推论

1. 可迁移的积累（判断标准、系统思维、推理链路）听着散，但**走到哪都带着**
2. 「懂得太多太杂」的真相：积累的是能力，不是业务知识——前者散，后者过时

## 六、什么样的「判断」算靠谱——四步取证，不许跳步

> 2026-11-18 从一次真实误判中提炼（Hermes 视觉路由复核）。

### 事故原样

复核 4 篇 Hermes 部署文档时，我看到 `config.yaml` 里没有 `auxiliary.vision`，就直接推断「视觉路由不存在，图片可能根本没被真正识别」，并据此给用户开了一个「恢复还是放弃」的决策题。

**查日志后真相完全相反**：Hermes 的 auto 路由发现主模型 deepseek 已支持看图，早已从 text（qwen 转述）自动切到 native（图片直接内联）。功能不但没坏，还比原先更好。

### 三层错误，逐层记下

| # | 错误 | 正确做法 |
|:-:|:--|:--|
| 1 | **把「配置缺失」当成「功能缺失」** | 配置只说明系统*被指示*怎么做；`auto` 模式下没有显式配置是**正常状态**。判断功能是否存在，看**运行证据** |
| 2 | **有证据渠道却没去查** | 判断任何运行时行为，**第一动作是查日志**（`/opt/data/logs/`），不是读配置。配置是意图，日志是事实 |
| 3 | **用「可能」包装猜测发出去** | 「可能」不会让猜测变谨慎，只会让它更难被反驳。**没有证据的判断，要么去拿证据，要么明确标注「未核实，需确认」** |

### 正确顺序：四步取证（2026-11-18 用户纠正后定稿）

> 我一开始的理解偏了：写成了「别只看配置，直接查日志」。用户纠正——**两个都要看，而且要按顺序看**。
> 真正的错误不是「看了配置」，而是**看完配置就下结论，跳过了对比**。

| 步 | 做什么 | 得到什么 |
|:-:|:--|:--|
| **1** | 看**系统指示**（配置 / 文档） | 系统*应该*是什么样 |
| **2** | 看**实际发生**（日志 / 运行数据） | 系统*实际*是什么样 |
| **3** | **对比差异** | 差在哪。**差异本身就是信息**——它说明意图与现实之间发生了什么 |
| **4** | **讨论，再下结论** | 有时间被别人质疑、有机会自己反证 |

🔴 **硬规则：不许在第 1 步之后就下结论。**

**这次如果做了第 3 步会立刻看清**：配置是 `image_input_mode: auto`（意图：让系统自己判断），日志是 `Image routing: native (model supports vision)`（现实：它判断了，选了 native）。**两者不是矛盾，而是完全一致**——auto 的意图就是自动判断。差异不存在，所以「功能坏了」这个问题从根上就不存在。

### 配套三条：推理要敢走，取证不许跳

> 2026-11-18 用户强调：「多走一步是好的，因为你可以看得比我更远，你比我更懂代码」。
> 这条和上面的取证纪律是**配套**的，不能只用一半——只用取证纪律会让人变得过度保守。

| 层面 | 规则 |
|:--|:--|
| **推理** | ✅ **多走一步**。能看清代码路径、配置语义、机制设计，这是价值所在，不要因为犯过错就缩回来 |
| **取证** | 🔴 **不许跳步**。四步走完再说结论 |
| **表达** | ⚠️ **区分「我查到的」和「我推断的」**。两者都可以说，但必须标明哪个是哪个 |

### 提炼成检查动作（不是「要小心」）

> **凡是要判断「某个功能现在还工作吗」「某个机制还生效吗」——不许从配置文件推断，必须去找运行痕迹。**

| 要判断的东西 | 去哪找证据 |
|:--|:--|
| 功能是否在工作 | 运行日志里有没有对应的调用记录 |
| 定时任务是否在跑 | `cron/jobs.json` 的 `enabled` + `last_run_at` + `last_status` |
| 配置是否生效 | 日志里打印的**实际取值**（如 `Image routing: native (mode=auto)`）|
| 服务是否健康 | 进程 / 端口 / 健康检查，不是看配置文件写得多完整 |

### 一条更普遍的推论

**「我以为丢了的东西，可能只是换了个更好的方式存在。」**

在动手恢复任何「丢失」的配置/文件/机制之前，先确认它**是不是已经不再被需要**。缺失有两种：一种是坏了，一种是进化了。只看静态快照分不出来，必须看运行轨迹。

## 七、这个笔记的用途

1. **写 SQL 前，拿第一条过一遍** —— 有没有先给结论？有没有带对比？
2. **设计新的 AI 工作流时，拿第二条过一遍** —— 是不是大脑+手脚？边界清楚吗？
3. **建新的体系时，拿第三条过一遍** —— 角色清晰吗？有容错吗？能迭代吗？
4. **评价一个人/公司/制度时，拿第四条过一遍** —— 看结构不看动机：他堵没堵别人的取水口？
5. **判断积累优先级时，拿第五条过一遍** —— 这是在公司的还是离开公司的？可迁移吗？
6. **判断某个功能/机制「还在不在工作」时，拿第六条过一遍** —— 四步走完了吗？看配置（应该）→ 看日志（实际）→ 对比差异 → 再下结论。**跳了后面三步就说话 = 把猜测当结论。**

> 这些标准不是固化的，它们应该随着我的工作经验变。
> 下次重读时，如果觉得哪条不对了，就改——那就是我在成长。
