# Hermes 跨平台会话接续规范

> 你在飞书和 CLI 之间切换使用 Hermes 时，如何保证对话不断裂、不烧冤枉 token。
>
> 适用场景：CLI 聊完 → 飞书继续；飞书聊完 → CLI 继续；隔夜后继续昨天的话题。

---

## 一、为什么切换平台不会「失忆」

Hermes 有三层保险，即使开新会话：

| 层 | 机制 | 效果 |
|:--|:----|:----|
| 🧠 **持久记忆** | MEMORY.md / USER.md 每个会话自动加载 | 你的偏好、规则、项目背景始终在 |
| 🔍 **会话搜索** | Hermes 能搜索历史会话记录 | 你说一个话题词，它自动去翻之前的聊天 |
| 📚 **知识库** | Obsidian vault 走 Git 同步 | 沉淀下来的结论永远在，跟实例无关 |

**核心：你切换平台时，Hermes 会主动去查另一边的聊天记录来衔接上下文——不需要你手动搬运。**

---

## 二、你只需要「提个话头」，不用记会话 ID

三种说法都行，按省事程度排：

| 你说 | Hermes 会怎么做 |
|:----|:--------------|
| 「接着昨天 CLI 聊的那个 XX」 | 用话题词精确搜索（最快最准） |
| 「昨天在 CLI 里聊的」 | 搜索最近 CLI 会话，自动挑相关上下文 |
| 「我们昨天聊到哪了？」 | 直接浏览最近会话，帮你找出来 |

**唯一要求：把话说全**——提一下「哪个平台」或「什么话题」，哪怕只有一个词（比如「数据字典」）。会话 ID 是 Hermes 自己用的，你不需要操心。

---

## 三、为什么要避免「跨夜的超长会话」（token 教训）

### 真实案例（2026-08-02）

「北宋二府三司制讨论」会话被系统记为 **16.6 小时**，实际你只聊了约 4 小时：

```
14:48 开始 → 活跃 2 小时（142 条消息）→ 你说「先到这儿」
⏸️ 挂机 11.3 小时（CLI 窗口没关）
04:08 你凌晨回来继续 → 又聊 2 小时（106 条消息）
```

**后果：** 凌晨继续聊时，模型每轮都要重读下午那 142 条历史——即使话题毫无关系。这一个会话烧掉 **1620 万 token，占 7 天总消耗的 42%**。

### 为什么「接得上」≠「全记住」

| 方式 | 接续效果 | token 成本 |
|:----|:--------|:----------|
| 同一条会话无限续（跨夜） | 100% 连续 | 🔴 高——历史越滚越大 |
| 开新会话 + Hermes 主动查 | 业务连续，关键结论都在 | 🟢 低——只带重点 |

**「接着聊」不需要模型把每句话重读一遍。** 开新会话 + 让 Hermes 查 = 接上了又省钱。

---

## 四、日常使用建议

| 场景 | 建议做法 |
|:----|:--------|
| 话题进行中（当天几小时内） | 继续用同一条会话，别关窗口 |
| 聊完说「先到这儿」后 | **关掉 CLI 窗口** 或 `/new` 开新会话 |
| 隔了一夜 / 跨天回来 | 开新会话，说「接着昨天的 XX」 |
| 长会话聊到一半感觉变慢 | 用 `/compress` 压缩历史 |

**一句话：别让一条会话跨过夜。** 下午的事下午了结，凌晨的新问题开新会话——这是最有效的省 token 方法（最多可省 40%+）。

---

## 五、为什么飞书 ↔ CLI 切换反而省 token

切换 = 天然的新会话，天然规避了长会话问题：

- 每次切换，Hermes 靠搜索把**关键上下文**接回来
- 不会出现「二府三司 16 小时 1620 万 token」那种情况
- 你要做的只是提个话头
