# 01-数据链路全景

> 一物一码数据从业务系统到看板的全链路映射：源系统 → 明细宽表 → 看板/报表
>
> 📌 2026-07-28 更新：基于 7/16 统计对齐会和 7/13 数据需求对齐会内容填充初版

## 核心主表

### 用户中奖记录表（record_user_line）

> 这是整个数据链路的**核心主表**，覆盖所有用户中奖后的全链路行为记录。

**关联表范围：**

| 关联表 | 关联键 | 用途 |
|:------|:-------|:----|
| 活动奖品配置表 | 奖品行 ID | 获取原奖品完整配置属性 |
| 独立膨胀配置表 | expand_option_id | 获取用户选中的膨胀奖品属性 |
| 扫码流水表 | 用户 ID + 时间 | 补充扫码行为数据、非中奖记录 |

### 关键字段映射

| 业务字段 | 数仓字段 | 说明 |
|:--------|:--------|:----|
| 活动标识 | `activity_number`（埋点）= 后台活动 ID | 活动级曝光数据直接从埋点层提取 |
| 中奖记录状态 | 保留 `1/2/3`，排除 `4`（作废） | 作废记录不纳入任何统计口径 |
| 获取方式 | `price_grant_mode` | 以用户最终选择的实际奖品配置为准 |
| 膨胀选择 | `expand_option_id` | 用户选中膨胀奖品后记录 |

## 宽表构建方案

### 临时方案（7月底前）

不直接开发固化看板，先用 **Hive 明细宽表** 支撑临时跑数：

```
字段范围：活动ID + 奖品属性 + 获取方式 + 膨胀状态 + 用户行为（全量关联）
存储位置：Hive 数仓
查询方式：业务侧通过自定义 SQL 灵活查询
```

### 理由

- 指标逻辑未完全验证前，避免看板重复开发
- 蔡鸿东的测试阶段跑数 SQL 可直接复用（替换表名即可）
- 先验证再固化，降低迭代成本

## 核心统计指标定义

### 活动级指标

| 指标 | 统计口径 | 说明 |
|:----|:--------|:----|
| **曝光人数** | 触发活动页埋点的唯一用户数 | 仅支持活动维度，不下钻到单奖品 |
| **参与人数** | 完成扫码并授权的唯一用户数 | 未登录/未授权不纳入 |
| **中奖人数** | 当前活动 100% 中奖，与参与人数等值 | 后续非100%中奖活动再拆分 |
| | | |

### 行为类指标

| 指标 | 统计规则 | 去重规则 |
|:----|:--------|:--------|
| 加C行为 | 以用户最终选的奖品对应行为为准 | 用户级：唯一用户去重 |
| 复购行为 | 同上 | 人次级：按实际发生次数 |
| 膨胀行为 | 同上，不单独统计初始与膨胀的关系 | 避免同一行为重复计数 |

### 费用类指标

| 指标 | 取值优先级 |
|:----|:----------|
| **活动履约费用** | ① 微信商户号实际到账数据（优先）→ ② 后台中奖记录发放状态（交叉校验） |
| **误差处理** | 以第三方渠道最终对账数据为准，不做人工修正 |

### 转化漏斗

```
曝光 → 参与 → 中奖 → 选择奖品 → 完成发放
```

每个节点的统计口径单独明确。发放完成判定以用户完成对应获取动作为准（加C/复购/直接领取），而非后台配置的发放动作。

## 统计筛选维度

### 筛选层级（固定顺序）

```
活动 → 奖品 → 获取方式 → 是否膨胀
```

### 各维度说明

| 维度 | 规则 |
|:----|:----|
| 活动 | 覆盖后台所有已配置的瓶内营销码活动，支持跨活动聚合 |
| 奖品 | 与所属活动强关联，仅展示当前选中活动下的奖品 |
| 获取方式 | 固定三类：加C / 第二瓶复购 / 直接领取（互斥），与券类型无绑定 |
| 膨胀 | 仅当奖品已配置膨胀选项时显示，无配置自动隐藏 |
