# 📐 知识库整理规范

> vault 的组织规则、分类约定、命名规范。**每次整理后催生的新规则都在此更新。**
>
> 关联：[[知识库首页]] · [[Obsidian + Hermes 工作流说明]]

## 一、目录结构与职责

| 一级目录 | 职责 | 存放什么 |
|:--------|:----|:--------|
| `个人成长/` | 自我认知、判断标准 | 关于我、AI观、判断标准、知识库首页、整理规范 |
| `业务分析/` | 工作方法、SQL、分析框架 | 方法论、专题分析、SQL 模式 |
| `企业沉淀/` | 从实战中提炼的可复用知识 | 数据架构、协作协议、团队管理框架 |
| `技能库/` | 系统怎么用（设计文档） | 多Agent协作设计、团队管理技能 |
| `笔记/` | 时效性内容（按月度归档） | AI日报、索引页 |
| `项目沉淀/` | 项目复盘 | 一物一码全量（原始纪要→三视角→决策提炼→全景） |
| `归档/` | 已过期的日常记录 | 日常沉淀、过期笔记 |
| `待办/` | 当前任务清单 | 讨论决定事项 |

## 二、命名规范

### ✅ 可复用内容 — 不用日期前缀

```
协作协议与方案BC定型.md           ← 对
三省六部运行纪要.md                ← 对
超级个体到超级团队-协调者生长框架.md  ← 对
```

### ✅ 日常归档 — 日期前缀

```
2026-07-22-项目日志.md           ← 对
AI每日简报 2026-07-27.md          ← 对（按月度目录归档）
```

### ✅ 统一写法

- AI 日报统一用 `AI每日简报`（无空格），不用 `AI 每日简报`
- wikilink 引用时统一用 `[[路径/文件名|显示名]]` 格式
- frontmatter 必加 `created` 和 `tags`

### ❌ 避免

- 用系统概念名做大目录（如 `三省六部/` → 应改为 `多Agent协作/`）
- 文件名混空格和日期前缀（如 `AI 每日简报 2026-07-25.md`）
- 文件和目录名中英文混搭（统一中文）

## 三、分类约定

### 技能库 vs 企业沉淀

```
技能库/          = 设计态：系统怎么设计的（角色定义、架构、技术方案）
企业沉淀/        = 运行态：实战中积累的经验、协议、踩坑记录
```

两者互补不重复。技能库索引中标注了企业沉淀中的关联文档。

### 数据字典

```
数据字典/         = 平铺，不分子目录（当前12张表，到30+再评估）
数据字典索引.md   = 按业务域分类的入口（CDP/埋点日志/电商/企微/公域/一物一码）
数据仓库分层说明.md = 架构总览，与数据字典并列
```

### AI 日报

```
笔记/2026-07/    = 按月归档
笔记/AI每日简报索引.md = 入口：时间线 + 标签归类 + 研究方向追踪
```

### 关于我的两篇

| 文件 | 定位 | 更新节奏 |
|:----|:----|:--------|
| `关于我.md` | 静态快照版（当前画像、核心判断） | 季度级，重大认知变化时 |
| `关于我（持续构建）.md` | 动态演进版（每次对话的新认知） | 每次有新的认知就加 |

## 四、维护准则

### 改文件结构时

1. 搜索全 vault 引用 → 批量 patch
2. 更新对应的索引页（首页、技能库索引、数据字典索引等）
3. 更新企业沉淀索引和技能库索引中的交叉引用
4. 检查概念性引用（如"三省六部"作为系统名）是否需要保留原文
5. Git commit 后推送

### 新增文件时

1. 查目录结构表，确认属于哪个目录
2. 遵循命名规范
3. 更新对应的索引页
4. 在首页「是什么」列加一行
5. 如果催生了新规则 → 更新本规范

### 不确定时

**先问，不擅自决定。** 分类归属、文件拆分、命名方式拿不准时，先输出方案让用户确认再动手。

## 五、什么值得沉淀为文档

| 值得沉淀 | 不值得沉淀 |
|:--------|:----------|
| 组织规则（目录结构、命名约定） | 一次性任务（今天删了几个文件） |
| 工作流（多步操作流程，可复用） | 临时决策（不反复用的判断） |
| 判断标准（好坏对错的依据） | 纯信息查询（表结构、API参数） |
| 协作协议（和人的约定） | 项目待办细节（有时效性） |
| 认知更新（自我认知的变化） | 日常沟通记录 |
| 方法论（从实战提炼的可复用规则） | 会议原始记录（提炼后存决策即可） |

> **判断信号：** 这个结论/规则会不会影响未来多次操作？会不会反复查阅？如果答案是「会」，就值得沉淀。

## 六、沉淀触发机制（Hermes → 用户）

Hermes 在以下信号出现时主动询问「这个要不要沉淀」：

| 信号 | 例子 | 动作 |
|:----|:----|:-----|
| 结论会影响未来多次操作 | 命名规范、目录结构约定 | → 更新本规范 |
| 提炼出了可复用的方法 | 方案B/C 协议、5步操作法 | → 沉淀为技能或独立笔记 |
| 用户说出了新的判断标准 | "工具输出≠工具写入" | → 补进「我的判断标准.md」 |
| 操作需要 3+ 步且可能重复 | 数据字典新增 SOP | → 沉淀为 SOP 类笔记 |
| 自我认知有了变化 | "原来我是这样思考问题的" | → 补进「关于我（持续构建）.md」 |

### 配合方式

```text
用户：日常操作、提问
    ↓
Hermes：执行 → 过程中触发信号
    ↓
Hermes：主动问「这个要不要沉淀？」
    ↓
用户：决策（要 / 不要 / 改个方式）
    ↓
Hermes：执行沉淀 + 更新规范
```
