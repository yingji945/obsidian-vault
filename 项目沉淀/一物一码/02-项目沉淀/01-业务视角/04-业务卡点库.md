## 🔴 严重卡点（影响上线或预算）

### 1. 联营结算风险（7/22发现）

| 维度 | 内容 |
|:----|:-----|
| **问题** | 发券链路调用 C 端发券接口时，联营门店订单记录 0 元收入 → 系统自动触发给合伙人的补贴支出，造成真金白银损失 |
| **根源** | 929 固定分摊比例的发券链路常年未更新，无法适配本次活动的差异化核算要求 |
| **影响** | ⚠️ 可能导致项目叫停或延期 |
| **解决** | 转向 **企业卡券系统**（toB 卡券流程）：即享侧作为企业主体先采购咖啡券，再通过活动码兑换发放 |
| **待确认** | 企业卡券系统适配可行性评估中（杨酥侧），可能赶不上 8/1 上线节点 |

### 2. C端发券接口不可行（7/22确认）

| 维度 | 内容 |
|:----|:-----|
| **问题** | C端发券接口无法识别电商侧专属的免费发券类型，无规则可匹配收入分摊 |
| **备选方案** | ① 财务中台手动调账 ❌（不符合审计）② 订单系统新增收入字段 ❌（无业务逻辑支撑）③ 仅标注券类型后统一结算 ❌（联营自动补贴）|
| **唯一可行** | **企业卡券系统**（但需额外开发）|

### 3. 预算约束与方案选择困境（贯穿全程）

| 维度 | 内容 |
|:----|:-----|
| **原始预算** | V0方案 956万（现金红包税负 ~46万） |
| **核心矛盾** | 9.9元红包参与率高但税费高 → 降低红包金额又怕用户参与度低 |
| **金句** | 「就算测出9.9参与率更高，我们这个小BU支撑不了」——预算约束是贯穿全程的核心决策前提 |
| **最终** | 税负优化后降至 **330-350万**（即享平台券12-13万 + 门店券~300万） |

## 🟡 中等卡点（有方案但需落地）

### 4. P0级：券适用商品列表过滤（7/14确认）

| 维度 | 内容 |
|:----|:-----|
| **问题** | 券适用商品列表会展示秒杀商品，用户看到秒杀价与券价冲突 |
| **严重程度** | P0级，**严禁上线后暴露给用户** |
| **排期** | 要求研发侧优先调配资源，蔡鸿东当日输出开发排期 |
| **解决** | 过滤秒杀商品，仅展示可适用券的商品 |

### 5. 兑奖路径用户体验差（7/14）

| 维度 | 内容 |
|:----|:-----|
| **问题** | 用户点击「查看奖品」「去领取」后无明确引导，易忽略小字规则 |
| **方案** | ① UI 改造：高对比度、大字号兑奖提示 ② 新增「复购兑换」按钮 ③ 奖品名称统一标准化 |
| **状态** | 刘晋泽负责输出 UI 图 |

### 6. 跨账号兑奖异常（7/14）

| 维度 | 内容 |
|:----|:-----|
| **问题** | 用户添加 Luna 的微信号与瑞幸账号绑定微信号不一致 → 奖品无法到账 |
| **根源** | 历史遗留多账号问题 |
| **方案** | 在「我的奖品」页面底部增加脱敏会员编号展示，作为兑奖纠纷时的核对依据 |
| **状态** | 已排期，不额外做 C 端强提示 |

### 7. 商户号主体待确认（7/10财务会）

| 维度 | 内容 |
|:----|:-----|
| **问题** | 当前暂用北京主体商户号打款，是否需要切换为海南主体 |
| **待办** | 对接魏姐确认 |
| **影响** | 影响红包发放链路 |

## 🔵 已知限制（不可行，需接受）

### 8. 细分渠道费用不可区分（7/22确认）

| 维度 | 内容 |
|:----|:-----|
| **问题** | 财务需统计各渠道红包/券发放金额用于费用记账 |
| **能力局限** | 线上货品无统一标识 → 抖音/京东等细分渠道不可拆分 |
| **可行范围** | 仅能通过经销商归属信息区分 **线上/线下** 两大维度 |
| **建议** | 接受粗颗粒度，不做细分渠道开发 |

### 9. 活动空档期合规风险（6/4讨论）

| 维度 | 内容 |
|:----|:-----|
| **问题** | 活动切换期设置空档期可降低合规风险，但可能导致用户扫码无响应 |
| **决策** | 按**无缝衔接**推进，在规则告知时做好活动衔接说明 |
