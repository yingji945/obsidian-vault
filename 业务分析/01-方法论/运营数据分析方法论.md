## 一、漏斗分析原则

### 1.1 链路归因：每一步都要有明确约束

```sql
-- 模板：三层漏斗，同日期约束
WITH step1 AS (  -- 第一步：入口
  SELECT user_id, dt
  FROM table_a
  WHERE ...
),
step2 AS (  -- 第二步：行为
  SELECT user_id, dt
  FROM table_b
  WHERE ...
),
step3 AS (  -- 第三步：转化
  SELECT mem_id, dt, income
  FROM table_c
  WHERE ...
)
SELECT
  COUNT(DISTINCT s1.user_id) AS step1_uv,
  COUNT(DISTINCT s2.user_id) AS step2_uv,
  COUNT(DISTINCT s3.mem_id)  AS step3_uv,
  COALESCE(SUM(s3.income), 0) AS total_income
FROM step1 s1
LEFT JOIN step2 s2 ON s1.user_id = s2.user_id AND s1.dt = s2.dt
LEFT JOIN step3 s3 ON s2.user_id = s3.mem_id AND s2.dt = s3.dt
```

### 1.2 严格漏斗 vs 独立统计（2026-11 实战补充）

上面这个模板**各级是独立统计的**（`count(distinct s1.user_id)`、`count(distinct s2.user_id)` 各自为政），会出现**下级大于上级**的倒挂。

**实测案例**：门店商品漏斗跑出「下单人数 94,662 > 点击人数 28,439」。原因不是字段语义错，而是有人没点商品、从历史订单/收藏/搜索直达商详下单。

**严格漏斗的正确写法**——每级累积前面所有条件，保证 `L(n+1) ⊆ L(n)`：

```sql
count(distinct if(bw = 1, mem_id, null))                                              as L1_曝光
count(distinct if(bw = 1 and ck = 1, mem_id, null))                                   as L2_点击
count(distinct if(bw = 1 and ck = 1 and card_ck = 1, mem_id, null))                   as L3_卡片点击
count(distinct if(bw = 1 and ck = 1 and card_ck = 1 and detail_bw = 1, mem_id, null)) as L4_商详
```

**两个必说的副作用**：
- 按天的严格漏斗要求全链路**同一天**完成（今天曝光、明天点、后天买就断链），人数会小到失真 → 必须同时给「周期严格漏斗」并说清报数用哪个
- 交付前跑一遍相邻两级比值检查，**任一 > 100% 就是自己写错**

### 1.3 常见坑点

| 问题 | 后果 | 修复 |
|:----|:-----|:-----|
| `LEFT JOIN` 只关联用户不关联日期 | 同用户不同天的数据交叉，金额翻倍 | 关联时加上 `AND date = date` |
| CTE 内预关联下游表 | 下游表数据被上游多行重复匹配 | 只在最终 SELECT 时 join |
| OR 条件包含 JSON 解析 | 全表触发 JSON 解析，极慢 | 拆成 UNION ALL |
| `prop_query_source IS NULL` 兜住自然流量 | 但未归因的投放流量也被兜入 | 看业务场景决定是否保留 |
| 从表 CTE 漏了关键标识条件 | `count(从表.id)` 把全部人算成转化 | CTE 的 where 里直接筛掉，或 `count(distinct if(o.flag = 1, o.id, null))` |

## 二、复购分析（2026-11 门店即享实战补充）

### 2.1 T0 当天不能算复购

复购窗口若写 `date(pay_time) >= t0`，而 T0 本身就是「首次购买该商品」那天，**首购这一笔必然落进窗口** → 每个人复购率恒等于 100%。

- 严格口径：`> t0`
- 宽松口径：`not (cmdty_code = '首购商品' and datediff = 0)`
- **两个口径一起给、分别命名**

### 2.2 比复购率必须统一观察窗口

按首购周/月分组直接算复购率，等于把「人群质量」和「观察期长度」混在一起——晚进来的人窗口天然短，复购率必然被压低，**能推出任意方向的假结论**。

正确做法：设 `t0_cutoff = obs_end − N`，只留 `t0 <= t0_cutoff` 的人（人人有完整 N 天），再看 `T0+1 ~ T0+N`。

**实测**：某商品五周 7 天复购率 17.77% / 15.76% / 12.17% / 18.07% / 12.54%，**无趋势** → 复购率是「这批人 + 这个品」的固有属性，与何时进入无关。

### 2.3 比较不同商品前先查上线日（左截断）

商品 A 上线早、B 上线晚，B 的「首复购天数」被 `最晚上线日 − t0` **左截断**，看起来「周期更长」纯是假象。

**实测**：某品 11-05 才上线只有 13 天窗口，算出「首复购 13.8 天」，而主力品 37 天窗口是 6.1 天 —— 差点得出「A 是零食、B 是口粮」的错误结论。统一切到 13 天窗口后，结论完全反转。

**规则**：多品对比前**先问每个品的上线日**，把窗口统一到最晚上线日之后。

### 2.4 复购率必须配客单价

只看复购率会误判。**实测**：某商品门店复购率 16.27% 看着不错，但客单价只有 11.72 元 —— 买的是最便宜的小包装，是**小额补货**不是消费升级。

**三个数必须一起给**：复购率、复购客单价、平均首复购天数（决定触达时点）。

## 三、对照组：判断「有效 / 无效 / 增量」的唯一方法（2026-11 核心补充）

**任何转化率、复购率、留存率，单看数值都无法判断好坏。先问一句：对照组是谁？**

### 3.1 三个账本不能混

| 账本 | 问题 | 指标 |
|:--|:--|:--|
| **渠道账** | 水往哪流？| 各渠道购买率 vs 对照 |
| **品牌账** | 池子有没有变大？| 新客占比 + 沉默唤醒占比 vs 渠道搬运占比 |
| **留存账** | 走了没有？| 唤醒后 N 天内回线上复购率 |

**实测三者拼起来才有完整判断**：渠道账（自营 6.7×）+ 品牌账（98.11% 真增量）+ 留存账（1.37% 留存失败）= **「入口不是容器」**。**只用其中一本账会得出片面甚至相反的结论。**

### 3.2 标准对照设计

| 要素 | 实验组 | 对照组 | 必须一致 |
|:--|:--|:--|:--|
| 人群来源 | 做了目标行为 | 同场景但**没做该行为** | 同期间、同城市、同门店 |
| 起点 T0 | 首次做目标行为日 | 首次同场景消费日 | 起点性质对齐 |
| 历史状态 | 新客（T0 前无单）| 新客 | 同「新客/沉默」状态 |
| 观察窗口 | T0 + N | T0 + N | **窗口长度必须相同** |
| 人群截断 | `t0 <= obs_end − N` | 同 | 保证人人有完整窗口 |

**唯一允许不同的是「有没有做那个行为」。**

### 3.3 实测：三个结论全部翻转

| 渠道 | 实验组 | 对照组 | 倍数 | 无对照时的误判 |
|:--|--:|--:|--:|:--|
| 自营购买率 | 0.20% | 0.03% | **6.7×** | 曾判「渠道断了」，实为**有效但极弱** |
| 公域购买率 | 3.20% | 3.26% | **1.0×** | 曾判「价值最高的路径」，实为**无额外提升** |
| 沉默唤醒率 | 1.37% | 0.54% | **2.54×**（p≈0.01）| 曾判「老客固有行为」，实为**真增量** |

### 3.4 分母必须同性质

一边人人有记录、一边只有部分有记录时，必须把两边都缩到「可观测人群」。

**实测**：自营人人有订单记录，分母天然是全体（0.31%）；公域只有 16.5% 有账号绑定，用全量分母算出 0.53% 会严重低估，正确是绑定分母 3.20%。**渠道对比必须用可观测分母，算总账才用全量分母。**

### 3.5 小样本只报方向，不报倍数

- n < 30：报方向 + 显著性检验 + 置信区间
- 实测：自营 A 组 8 人 → `95%CI 0.087%~0.394%`；公域新会员 20/48 → `95%CI 27.7%~55.6%`；沉默唤醒 7 人 → `z≈2.57, p≈0.01`
- **汇报写「显著高于基准」，不写精确倍数**

### 3.6 四类选择偏差

| 偏差 | 表现 | 破解 |
|:--|:--|:--|
| 有账号 = 老用户 | 把 3.20% 当基准行为 | 按**入会时间 vs T0** 拆开 |
| 老客 = 活跃 | 把 898 个沉默用户当活跃老客 | 按**距上次购买天数**分档（90/365）|
| 绑定池重复匹配 | 金额放大近一倍（6,345 vs 3,495）| 按 `mem_id` 聚合后再关联订单 |
| 平台串号 | 跨平台匹配错人 | `hmp.platform = tpo.platform` 两边都限 |

## 四、口径自洽：不做无意义的运算

**做任何加减乘除前过一遍五问：**

| 问自己 | 反例 |
|:--|:--|
| 两个数的**分母人群**一致吗？ | 938 人（7,057 分母）− 389 人（2,827 分母）→ 无意义 |
| 两个数的**观察窗口**一致吗？ | 6.1 天（37 天窗口）vs 13.8 天（13 天窗口）→ 不可比 |
| 这个数是**收入**还是**成本**？ | 把人均支付 7.82 元当采购成本 → 错 |
| 这个数是**人次**还是**人数**？ | 34.7% 人次占比 ≠ 人数占比 |
| 这个数是**应付**还是**实付**？ | `cmdty_pay_amt` 与 `new_user_pay_money` 差 0.44~3.23 元 |

**一句话**：要做比较，先让两边的**分母、窗口、人群**三样都对齐；对不齐就分开报，别做四则运算。

### 跨渠道识别新客的陷阱

用「另一条业务线从未有有效订单」筛出的「新客」，实际可能是在别的渠道早已高频消费的老客。

**实测**：门店即享成交用户 **91.6%** 在自营电商无任何订单，看似巨大增量池，但其中对自营的后续复购率只有 **0.31%**（同期同类引流品 3.96%，差 8 倍）。

**规则**：给出「N% 是新客」时**必须同时给后续转化率**，否则会把「渠道割裂」误报成「增量池」。写成「线下已成交、线上未触达」比写成「新客」准确。
