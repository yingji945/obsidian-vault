# SQL 经验库

## 基础规范

### 日期写法
| 错误 | 正确 | 引擎 |
|:----|:-----|:-----|
| `now()` | `current_date()` | Spark SQL |
| `DATEDIFF(month, ...)` | `months_between(...)` | Spark SQL |
| `date_sub(now(), 1)` | `date_sub(current_date(), 1)` | Spark SQL |

### WHERE 条件
```sql
-- ❌ 错误：OR 写法，永远为 true
event_code = 'a' or 'b'

-- ✅ 正确
event_code IN ('a', 'b')

-- ✅ 区间用半开
event_time >= '2026-07-01 00:00:00'
AND event_time <  '2026-07-02 00:00:00'
```

## 性能优化

### Broadcast Hint
```sql
/*+ broadcast(小表名) */
```
小表 join 大表时加，避免 shuffle。

### OR 拆 UNION ALL
```sql
-- ❌ 慢：OR 阻止分区下推，JSON解析落到全表
WHERE (event_code = 'web_page_start' AND json条件)
   OR event_code IN (多个值)

-- ✅ 快：拆成两个子查询 + UNION ALL
WHERE event_code = 'web_page_start' AND json条件
UNION ALL
WHERE event_code IN (多个值)
```

### get_json_object
- 每条记录都要解析 JSON，非常慢
- 能过滤先过滤，让 JSON 解析只落在需要的行上
- `LIKE '前缀%'` 比 `LIKE '%任意%'` 快（前缀匹配可优化）

## 🔧 对话修正记录

> 每当我帮你改 SQL 时发现的常见错误，按时间倒序排列。新手入组可以先翻这部分。

### 2026-07-28 | 用户分层SQL — 全量快照表不需要加时间下限

**场景：** 写新客/留存/沉默分层，`t1` 里自动加了 `>= '2024-01-01'`

❌ `where dt = date_sub(current_date(), 1) and date(eorder_pay_time) >= '2024-01-01'`
✅ `where dt = date_sub(current_date(), 1)` 即可

**💡 原因：** `dws_eorder_eorder_d_his_combine` 是**全量快照表**，一个分区包含所有历史订单，加下限反而会丢失历史数据（沉默用户就判断不出来了）。
**预防原则：** 写 SQL 前先确认表模型——全量快照 vs 增量分区 vs 拉链表，确定是否需要时间下限。

### 2026-07-28 | 用户分层SQL — 窗口参数只改一处

**场景：** 你说要支持 Q1/H1 切换，我一开始在 `target_users` 和 `left join o` 两处各自改

❌ 在 CTE `target_users` 和下游 `left join t1 o` 分别改窗口过滤
✅ 所有下游 CTE 从同一个 `t1` 派生，在 `t1` 加 `date(eorder_pay_time) <= '截止时间'` 一改全改

**💡 原因：** 数据流是 `t1 → 各CTE → final`，控制点只在 `t1`，不需要在每条支路都加阀门。
**预防原则：** 画数据流，找到**单一控制点**再下笔。如果所有支路都从同一个 CTE 衍生，只改那个 CTE。

### 2026-08-26 | 用户分层SQL — DATEDIFF(month) 3参报错 + 跨月窗口用户重复计数

**场景：** 7/20~8/3 窗口用户分层（新客/前3个月留存/沉默3个月回流），join 用 `DATEDIFF(month, b.ym, a.ym)`，且窗口横跨 7、8 两月

❌ `and DATEDIFF(month, b.ym, a.ym) between 1 and 3` — 编译报错 `Invalid number of arguments for function datediff. Expected: 2; Found: 3`
✅ `and months_between(to_date(concat(a.ym,'-01')), to_date(concat(b.ym,'-01'))) between 1 and 3`

❌ `a` 子查询按 `(ym, mem_id)` 去重 — 7月和8月都下单的用户出现两行，同一用户可能同时进「新客」和「前3个月留存」两个桶，人数/单量/收入重复计数
✅ `a` 按 mem_id 取 `min(ym)` 一个代表月，一人一行只归一类

**💡 原因：** ① Spark SQL 的 `datediff` 只支持 2 参（返回天数），3 参月份版是 SQL Server/Databricks 语法；`'2026-05'` 这类年月字符串直接进日期函数会解析失败返回 NULL，需 `concat('-01')` 补全成完整日期。② 分析窗口跨自然月时，按月粒度取用户会产生多行，跨桶重复计数。
**预防原则：** ① 月份差值一律用 `months_between(后面的日期, 前面的日期)`，年月字符串先 `concat('-01')` 再 to_date，别用 3 参 DATEDIFF；② 窗口跨月时，分层基准先按 mem_id 去重（取 `min(ym)`）再分类，避免一人进两桶。

### 2026-11-05 | 引流品/试用装转化分析 — 四处口径坑（实战，踩了三处）

**场景：** 评估 9.9 元试用装 SKU 的真实转化价值，需要 新客分层 → 30/60/90 天转化 → 转化买了什么 三段分析

❌ 用 30 天窗口当真实转化率 → 算出 4.45%，差点判断"这条线该砍"
✅ 引流品必须给 **90 天**：30 天 4.45% → 60 天 5.82% → 90 天 **6.84%**，30 天口径低估 54%

❌ CTE 里先按月份聚合、外层才 `where pb.mem_id is null` 过滤老客 → 分子含老客、分母不含，转化率虚高（10 月算成 18.6%，实际 4.2%）
✅ 把"符合条件的人群"做成**唯一入口 CTE**（如 `new_users`），分子分母全部从它派生，不在下游补过滤

❌ 把"人次"当"人数"读 → 误以为 34.7% 的转化者在买小样
✅ 分档统计后必须**按人去重**（`group by mem_id` 再分类），实际只有 3.3% 只买低价品

❌ 拿商品明细表当订单表用（`fact_dwd_eord_eorder_commodity_d_his` 没有 `eorder_pay_time` / `eorder_status` / `merchant_type`）
✅ 明细表只负责 SKU 与金额，时间/状态/自营口径**一律 join 订单主表** `dws_eorder_eorder_d_his_combine` 取

**💡 原因：** ① 引流品的体验+决策周期普遍 3~8 周，首月只能捞到 2/3；② 预聚合后外层过滤是"两个数据源"的经典错位——聚合结果已经丢了明细行，没法再筛；③ 一人可跨多个价格档，人次恒大于人数；④ 电商明细表只存商品行属性，订单状态是订单级信息。

**预防原则：** ① **评估周期写进模板**，引流品一律 90 天；② **唯一入口 CTE** 模式——任何"人群筛选"只做一次，下游全部引用它；③ 分档/分布类统计**先按人去重再下结论**；④ 写 SQL 前先确认"这张表有没有时间列和状态列"，没有就 join 主表。

### 2026-11-18 | 门店即享复购分析 — 六处口径坑（全部踩了）

**场景：** 评估门店即享 SP4386 咖啡液的渠道价值，跑「门店买家 → 线上自营 / 门店 / 公域」三条复购路径 + 商品级漏斗，跨 `dwm`(Hive) 与 `ads_inst_*`(Doris) 两套表

❌ 复购条件写 `date(order_pay_time) >= t0` → T0 当天那笔「买目标商品」的单被算成复购，复购率算出 **100%**（复查购人数 = 总人数）
✅ 严格口径 `> t0`；宽松口径用 `not (cmdty_code = '目标品' and datediff(...) = 0)`

❌ 按时间段切分比复购率（前 25 天 vs 后 12 天）→ 得出「早期用户更会复购」
✅ 统一切到固定窗口（只留 `t0 <= obs_end - 7` 的人，看 `T0+1~7`），5 周实测 17.77/15.76/12.17/18.07/12.54%，**无趋势**

❌ 直接比不同商品的首复购天数（意式黑咖 6.1 天 vs 生椰 13.8 天）→ 差点得出「生椰是零食」
✅ 先查上线日：生椰 **11-05 才上线**，只有 13 天窗口，13.8 天是被左截断强行拉长的。统一切到 13 天窗口后：意式 13.76% vs 生椰 6.19%

❌ 用 `package_id is not null and package_id <> ''` 识别双杯套组 → 返回 **0 人**
✅ 用 `package_code like 'PF%'` / `'CHPF%'`（`package_id` 在 `dwm` 里对普通商品全空）

❌ 门店侧只加 `order_pay_time is not null` 当有效订单条件
✅ 还必须加 `order_status = 50` 和 `order_cmdty_situation <> 2`（本次仅剔除 1.49%，但差额应查不应猜）

❌ 漏斗各级都用 `count(distinct if(flag=1, mem_id, null))` → **下单人数 94,662 > 点击人数 28,439**，倒挂
✅ 严格漏斗要累积条件：`if(bw=1 and ck=1 and card_ck=1 and detail_bw=1 and pay_mem=1, ...)`

❌ 把「人均复购金额 7.82 元」当采购成本算加赠方案
✅ 那是消费者付的钱；成本要单独问。同表里 `cmdty_pay_amt`（应付）与 `new_user_pay_money`（实付）还差 0.44~3.23 元

❌ 直接在 Hive 跑 `dw_drs_ads.ads_inst_mem_cmdty_behavior_d_1d_uniq` → `Table or view not found`
✅ 该表在 **Doris**；同族表引擎大概率一致（`ads_inst_*` 两版都是 Doris，`dwm/dws` 都是 Hive）

**💡 原因：** ①「首次购买日」和「复购日」共用一个日期字段，条件写宽了就会自我循环；②观察期长度不齐时，任何按时间分组的比较都在比窗口而不是比人群；③新上市商品的复购间隔被「上线日」截断，会和成熟品形成虚假差异；④字段名相近不代表语义相同，`package_id`/`package_code`、`cmdty_pay_amt`/`new_user_pay_money`、`is_inst_ord_mem`（人级 vs 商品级）都是陷阱；⑤超半数「错误结论」不是算错，而是把不同分母、不同窗口、不同口径的数字做了加减乘除。

**预防原则：**
① **复购分析的第一个动作是排除 T0 当天**，写完先看复购率是否接近 100% 或 0%；
② **窗口一律统一**——所有比较对象给同样长度，报数时写明用的是哪个窗口；
③ **比较商品前先查上线日**，有任何一件晚上线就统一切到它的窗口长度；
④ **字段先用探针验证**（`group by 字段 limit 20` 看有没有值），不要按名字猜；
⑤ **有效订单三件套**：`order_pay_time is not null` + `order_status = 50` + `order_cmdty_situation <> 2`；
⑥ **严格漏斗要累积条件**，跑完检查各级人数是否单调递减；
⑦ **做任何运算前过一遍五问**：分母人群一致吗？窗口一致吗？收入还是成本？人次还是人数？应付还是实付？

### 2026-11-19 | 单个数字没有意义 —— 必须配对照组才能说「有效/无效」

**场景：** 评估门店即享对三条渠道（门店 / 自营 / 公域）的导流效果。有 7,017 个门店买家，能算出各自的后续购买率，但**这些比率本身无法判断好坏**。

❌ 只报比率：「门店→自营复购 0.31%，太低了，渠道断了」——0.31% 是高是低，取决于没买过的人是多少
✅ 建对照组：同期同城消费、但**没买该商品**的人（2,501,647 人），同样限新客、同样统一 T0+7 天窗口

**实测三个结论全部翻转：**

| 渠道 | 实验组 | 对照组 | 倍数 | 原判断 | 修正后 |
|:--|--:|--:|--:|:--|:--|
| 自营 | 0.20% | 0.03% | **6.7×** | 🔴「断了」 | ✅「有效但极弱」 |
| 公域 | 3.20% | 3.26% | **1.0×** | ✅「价值最高」 | 🔴「无额外提升」 |
| 沉默唤醒 | 1.37% | 0.54% | **2.54×** | — | ✅「真增量，p≈0.01」 |

❌ 公域用 7,017 作分母算 0.53%，与自营 0.31% 直接比 —— 自营人人有账号，公域只有 16.5% 有绑定，**分母性质不同，不可比**
✅ 给两个分母：**全量分母**（0.53%，算总账/预算用）、**绑定分母**（3.20%，渠道对比用）

❌ 「有公域账号 = 老电商用户 = 不会产生增量」
✅ 拆开看：入会早于 T0 的占 95.85%（1.53% 购买率，基准行为）；入会后于 T0 的仅 4.15%，但**转化 41.67%、27 倍**，人均贡献 39.04 元 vs 1.46 元

❌ 「老客 = 活跃用户」
✅ 按距上次购买天数分档：**沉默老客 898 人 vs 活跃老客 133 人 = 6.75 倍**。入会早只说明注册早，不说明最近在买

❌ 小样本倍数直接写进汇报（A 组 8 人 → 6.7 倍；沉默唤醒 7 人 → 2.54 倍）
✅ 报数时给区间与显著性：`z≈2.57, p≈0.01`（显著）；`95%CI 0.087%~0.394%`（方向确定、倍数不可写死）。汇报写「显著高于基准」，不写精确倍数

❌ 把「渠道维度」和「品牌维度」混成一个结论
✅ 两个账本：**渠道维度**问「水往哪流」（自营 6.7× / 公域 1.0×）；**品牌维度**问「池子有没有变大」（98.11% 是新客+沉默唤醒，渠道搬运仅 1.90%）。**渠道搬运为 0 不代表没增量，渠道有提升也不代表池子变大**

❌ 绑定池写 `distinct mem_id, platform, platform_member_id` 再 join 订单 → 同一人多平台账号重复匹配，**金额放大近一倍**（6,345.24 vs 真实 3,495.41）
✅ 按 `mem_id` 聚合后再关联订单；`hmp.platform = tpo.platform` 两边都要限

**💡 原因：** 比率天然没有参照系。0.20% 可以是「远高于基准的 6.7 倍」，也可以是「每千人只有 2 个，几乎为零」——**同一组数字，两种结论都对，取决于是跟谁比、跟什么口径比。** 而选择偏差（本来就活跃的人更可能出现在实验组）会让没有对照的结论系统性偏乐观或偏悲观。

**预防原则：**
① **任何「转化率/复购率/留存率」，先问一句「对照组是谁」** —— 答不出来就不要下有效/无效的判断；
② **对照组必须同源**：同期间、同城市、同门店、同「新客/沉默」状态，**唯一差异是要测的那个行为**；
③ **分母性质要一致**：一边人人有账号、一边只有部分有账号，就不能直接比绝对值，必须缩到可观测人群；
④ **「有记录」≠「活跃」**：涉及老客的结论，一律先按距上次行为的天数分档（90 / 365），别用「注册时间」代替「活跃度」；
⑤ **n < 30 只报方向不报倍数**，并附显著性检验与置信区间；
⑥ **多维结论要分账本**：渠道账（流向）、品牌账（总量）、留存账（持续性）各自独立，不要用一个结论覆盖三个问题。
