# 数据字典维护规范

> 本文档面向数据字典的维护者（Hermes 或后续接手的人），说明新增、修改、删除表文档的流程。

---

## 新增一张表

### 触发条件

- 用户发送 `SHOW CREATE TABLE` 或 `SELECT` 完整字段列表
- 发现数仓中新增了之前未记录的表

### 执行步骤

```
用户发 DDL
    ↓
第1步：建表文档 → 企业沉淀/数据字典/{表名}.md
第2步：更新索引 → 企业沉淀/数据字典/数据字典索引.md
第3步：关联相关表 → 对应的表文档加上双向链接
第4步：git commit + push
```

#### 第1步：建表文档

每张表独立一篇，包含以下章节：

| 章节 | 内容 | 必须 |
|:----|:-----|:----|
| YAML frontmatter | `created`, `updated`, `tags`, `field_status`, `source` | ✅ |
| 表名 + 数据库 | 完整表名、所属数据库 | ✅ |
| 表结构 | 字段名、类型、说明（带编号表格） | ✅ |
| 关联键 | 关联了哪些表、用什么字段 join | ✅ |
| 使用注意点 | 分区、口径、陷阱、常见误解 | ✅ |
| 典型 SQL | 1~3 条常用查询示例 | 推荐 |
| 关联 | 双向链接到相关表、索引页 | ✅ |

**字段分组规则**：字段多时按逻辑分组（基础标识/时间戳/金额/状态等），每组一个小表格。

**字段清单格式**：

```markdown
| # | 字段名 | 类型 | 说明 |
|:-:|:------|:----|:-----|
| 1 | `id` | bigint | 自增主键 |
```

#### 第2步：更新索引

在 `数据字典索引.md` 中：

1. 找到对应的**业务域**（企微/公域/电商/一物一码/埋点日志）
2. 新增一行：`| [[表名]] | 说明（含字段数） | ✅ 完整 |`
3. 如果表属于新的业务域，在合适位置新增一个域名 + 表格

**索引表格格式**：

```markdown
## XXX域

| 表名 | 说明 | 字段数 | 层级 |
|:----|:-----|:-----|:----|
| [[表名]] | 简短说明 | N | `ODS/DWD/DWS` |
```

#### 第3步：关联相关表

- 在相关表的文档末尾「关联」行加上新建表名的双向链接
- 如果是 ODS→DWD 的数据血缘关系，标注 `（数据源ODS）`

#### 第4步：提交

```bash
cd /opt/data/obsidian-vault
git add -A
git commit -m "数据字典：新增 {表名} {N}字段"
git push origin main
```

## 修改一张表

### 触发条件

- 字段变更（新增/删除/改名/改类型）
- 使用注意点需要补充（踩了新的坑）

### 执行步骤

```
第1步：更新表文档
第2步：如果字段数变化，更新索引中的说明
第3步：git commit + push
```

### 版本记录

在文档的 YAML frontmatter 中更新 `updated` 字段，并在注意点中标注变更：

```
> ⚠️ 2026-07-25 更新：新增了 {字段名} 字段，用于 {说明}
```

---

## 删除一张表

不建议实际删除文档，改为在索引中标记为「已废弃」：

| `[[表名]]` | 原说明 | N | 层级 | ❌ 已废弃 |

保留历史记录供回溯。

---

## 通用原则

1. **完整优先于完美**——字段太多可以先建框架，标 `🟡 待补充`，等用户发 DDL 再补全
2. **每张表独立一篇**——不合并，方便搜索和链接
3. **关联不能断**——新增表必须检查是否有相关表需要加链接
4. **commit 信息清晰**——`数据字典：新增/修改 {表名} {N}字段` 的格式
