# 门店订单渠道层级总览

**适用表**：[[dwm_mg_order_cmdty_market_wide_d_view]]、`dwm_mg_order_cmdty_market_wide_d_inc`、[[dwm_mg_order_cmdty_channel_bridge_d_inc]]

> **为什么单独写一篇**：门店订单表有 `first/second/third/fourth_channel_name` 四级渠道字段，四级各取什么值、哪一级才是「美团」这种业务口径，**只能一层层探出来**。不记下来，下次用要重探一遍。
> **实测数据**：2026-11-02 ~ 11-22（21 天），全国所有门店，`order_status = 50` + `order_cmdty_situation <> 2` + 有 `package_code` 的订单，共 **5,570,941 单**（去重后）。

---

## 一、渠道树（实测四级对应关系）

```
公域  3,640,746  (65.35%)
├── 公域到家  3,541,686  (97.28%)
│   ├── 美团外卖      2,525,812   69.39%   → 四级：美团外卖
│   ├── 淘宝闪购        883,752   24.28%   → 四级：淘宝闪购外卖
│   └── 京东外卖        132,122    3.63%   → 四级：京东外卖 132,121 + 京东甄选 1
└── 公域到店     99,060  (2.72%)
    ├── 美团到店         98,829    2.72%   → 四级：美团到店-团购
    └── 到店其他            231   0.006%   → 四级：淘宝闪购到店

私域  1,930,195  (34.65%)
├── 交易渠道  1,643,007  (85.01%)   ← 实际下单渠道
└── 引流渠道    289,625  (14.99%)   ← 引流来源
```

### 各级字段取值

| 层级 | 字段 | 实测取值 |
|:--|:--|:--|
| **一级** | `first_channel_name` | `公域` / `私域` —— **只有这两种，无空值** |
| **二级** | `second_channel_name` | `公域到家` / `公域到店` / `交易渠道` / `引流渠道` |
| **三级** | `third_channel_name` | `美团外卖` / `淘宝闪购` / `京东外卖` / `美团到店` / `到店其他` |
| **四级** | `fourth_channel_name` | `美团外卖` / `淘宝闪购外卖` / `京东外卖` / `京东甄选` / `美团到店-团购` / `淘宝闪购到店` |

## 二、关键结论

### 2.1 🎯 三级就是业务口径，四级没有额外信息

四级和三级基本 1:1 映射，**全部 364 万公域单里只有 1 单被四级拆出了差异**（京东外卖 → 京东甄选 1 单）。

| 三级 | 四级 | 增量信息 |
|:--|:--|:--|
| 京东外卖 | 京东外卖 + 京东甄选 | 仅 1 单，可忽略 |
| 美团到店 | **美团到店-团购** | 🎯 明确是**团购券模式**（买券到店核销），不是到店自提 |
| 到店其他 | **淘宝闪购到店** | 补上渠道名 |

**做渠道分析取到 `third_channel_name` 就够，不要下探四级。** 唯一值得记的是「美团到店 = 团购券核销」。

### 2.2 没有「饿了么」

公域外卖只有三家：**美团外卖、淘宝闪购、京东外卖**。整个渠道体系里没有饿了么。

> 与瑞幸渠道策略一致（美团合作，不上饿了么）。以后讨论「公域外卖」时指的是这三家。

### 2.3 美团外卖是公域的代名词

美团外卖 252 万单，**比第二（淘宝闪购 88 万）和第三（京东外卖 13 万）加起来还多 1.5 倍**。

- 只想看一家 → 看美团外卖
- 淘宝闪购是真正的第二极，是京东的 **6.7 倍**，两者不在同一量级
- 公域到店团购链路只占 2.72%，是边缘链路，放量属异常

### 2.4 🔴 私域的二级渠道不互斥

| | 一级探针（按 `first_channel_name` 去重）| 二级加总 |
|:--|--:|--:|
| 公域 | 3,640,746 | 3,640,746 ✅ 差 0 |
| **私域** | **1,930,195** | **1,932,632** ❌ **多 2,437** |

**有 2,437 单同时带「交易渠道」和「引流渠道」两个二级值。** 占私域 0.13%，量小，但意味着：

> 🔴 **二级渠道订单量不能直接加总当总量** —— 交易渠道 + 引流渠道 ≠ 私域总量。

原因：一单可能是「通过引流渠道进入、在交易渠道下单」，两个标签都会打上。**总量一律以一级 `first_channel_name` 去重为准。**

公域没有这个问题（公域到家 + 公域到店精确等于公域总量）。

### 2.5 🎯 套餐类型对应 `package_type` 字段（比前缀匹配可靠）

`dwm_mg_order_cmdty_market_wide_d_view.package_type` 枚举：**1 = 自营套餐，2 = 渠道套餐**。

这与 `package_code` 前缀完全对应：

| `package_code` 前缀 | `package_type` | 业务含义 | 实测渠道归属 |
|:--|:--:|:--|:--|
| **`PF%`** | **1 自营套餐** | 私域小程序自有套餐 | 私域 **99.99%**（31,917 / 31,920）|
| **`CHPF%`** | **2 渠道套餐** | **CH**annel **PF** —— 外卖渠道套餐 | 公域 **100%**（59,938 / 59,938）|

**结论：PF 和 CHPF 不是两档产品，而是同一套套餐在两条渠道体系里的两个版本。** 认定套餐类型时**优先用 `package_type` 字段**，不要靠 `package_code LIKE 'PF%' / 'CHPF%'` 前缀匹配——前缀是命名约定，字段才是数据契约。

> 实测还发现：**公域有 3 单带 `PF%` 前缀**（金额 74.40 元），**私域 0 单带 `CHPF%` 前缀**。交叉近乎完全干净。

## 三、标准用法：每单钉唯一渠道

因为存在一单多渠道，直接 `group by third_channel_name` 会把订单算多次。**正确做法是先给每单钉一个唯一渠道**：

```sql
order_channel AS (
    SELECT o.dt
         , o.order_id
         , MAX(o.first_channel_name)  AS l1
         , MAX(o.second_channel_name) AS l2
         , MAX(o.third_channel_name)  AS l3
    FROM dw_dwm.dwm_mg_order_cmdty_market_wide_d_view o
    WHERE o.dt BETWEEN '2026-11-02' AND '2026-11-22'
      AND o.order_status = 50
      AND o.order_cmdty_situation <> 2
    GROUP BY o.dt, o.order_id
)
```

`group by dt, order_id` + `MAX()`：一单多值取其一。**这样「订单量」一定是去重订单数，不会因渠道层级变深而虚高。** 代价是 2,437 单重叠的被归到其中一个渠道，但总量准确。

### 渠道标签推荐写法

```sql
, CASE WHEN c.l1 = '公域'
       THEN COALESCE(c.l3, c.l2, '公域-未分类')   -- 公域取三级
       ELSE COALESCE(c.l2, '私域-未分类')          -- 私域三级为空，退回二级
  END AS channel_group
```

私域的 `third_channel_name` 实测为空，所以必须 `COALESCE` 退回二级（交易渠道 / 引流渠道），否则整批私域单会掉进「未分类」。

## 四、验证 SQL

### 4.1 各层级取值分布（探针，改层级即可）

```sql
select first_channel_name
     , second_channel_name
     , third_channel_name
     , count(distinct order_id) as 订单量
from dw_dwm.dwm_mg_order_cmdty_market_wide_d_view
where dt between '2026-11-02' and '2026-11-22'
  and order_status = 50
  and order_cmdty_situation <> 2
  and package_code is not null
  and trim(package_code) <> ''
group by first_channel_name, second_channel_name, third_channel_name
order by 订单量 desc
```

### 4.2 层级一致性校验（必跑）

```sql
-- 一级 vs 二级加总，差值不为 0 就说明该层有重叠
select first_channel_name
     , count(distinct order_id)                          as 一级去重
     , sum(cnt)                                           as 二级加总
     , sum(cnt) - count(distinct order_id)                as 差
from (
    select first_channel_name, second_channel_name
         , count(distinct order_id) as cnt
         , min(order_id) as dummy
    from dw_dwm.dwm_mg_order_cmdty_market_wide_d_view
    where dt between '2026-11-02' and '2026-11-22'
      and order_status = 50
      and order_cmdty_situation <> 2
      and package_code is not null
      and trim(package_code) <> ''
    group by first_channel_name, second_channel_name
) t
group by first_channel_name
```

## 五、即享售卖门店的渠道结构（2026-11-02~11-22）

| | 公域占比 | 私域占比 | 订单量 |

## 六、使用注意点

| # | 注意点 | 说明 |
|:-:|:--|:--|
| 1 | 🔴 **一单可带多个渠道值** | 私域尤其明显（2,437 单重叠）。**必须按订单钉唯一渠道再统计**，否则订单量虚高 |
| 2 | 🔴 **二级不能加总当总量** | 总量一律用 `first_channel_name` 去重 |
| 3 | 🟡 **三级到顶了** | 四级仅多拆出 1 单，不值得下探 |
| 4 | 🟡 **私域三级为空** | 必须 `COALESCE(l3, l2)` 退回二级 |
| 5 | 🟡 **`dwm_mg_order_cmdty_channel_bridge_d_inc` 是另一条路** | 专门的渠道桥接表（4 字段）。本宽表自带四级字段时不必用它；如果宽表渠道字段缺失或口径存疑，再查桥接表交叉验证 |
| 6 | 🟡 **`feature_shops` 取最新分区快照** | 分析跨多天时，期间新开/关闭的门店集合会有轻微不一致 |
